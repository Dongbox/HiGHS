# 阶段 1：解析与测量 MindOpt

固定目标为本机 Apple Silicon 的 MindOpt 2.3.0 SDK。每个二进制以 SHA-256 标识，地址只在对应构建与切片内有效。后续分析先复用现有 Evidence 和快照，避免重复导入或扫描。

| 编号 | 要回答的问题 | 需要的证据 | 状态 |
| --- | --- | --- | --- |
| P1-01 | CLI、Python、C API 与核心库的边界是什么？ | Mach-O 导入/导出、入口反编译、关键调用路径 | 部分完成：CLI 入口及核心 C API 清单已记录 |
| P1-02 | LP、MILP、MIQCP 等模块如何被选择和加载？ | 求解入口与模块加载器的引用/调用关系，选定模型的运行轨迹 | 未完成；文件名及 dlopen 导入只能提供线索 |
| P1-03 | 单模型内部如何并行？ | 线程创建方、任务提交/窃取、队列、同步、共享状态及相应运行观察 | 未完成；已发现线程相关导入，尚未归因 |
| P1-04 | 多个独立模型同时求解的瓶颈是什么？ | 进程/Env 生命周期实验，授权时间、吞吐量、CPU/内存与线程数 | 未完成 |
| P1-05 | 提速来自哪些工作？ | presolve、根节点、LP/线性代数、cuts、heuristics、树搜索的分阶段时间与受控实验 | 未完成 |
| P1-06 | 哪些设计值得在 HiGHS 验证？ | 与统一性能基线相连的假设、HiGHS 源码落点、验证和否定条件 | 未完成；已建立 HiGHS 源码地图 |

先追踪核心库中的 `MDOoptimize`，再依据实际调用边界进入 LP 或 MILP 模块。优先围绕具体问题做函数级分析，不把所有反编译输出堆成“源码恢复”。线程库的导入也可能来自授权心跳、I/O 或其他辅助工作，必须追踪调用方后再归因。

每条研究结论记录目标哈希、地址、工具/版本、Evidence ID、证据类型、观察范围、推断及剩余未知。静态依赖或符号不能证明运行时实际走过某条路径。重要伪代码逻辑用汇编及调用关系交叉检查。

运行实验使用正常社区版联网授权，并显式释放 Model 和 Env。授权耗时与求解耗时分开记录；实验不改变授权逻辑。涉及论文 PDF 或数学公式 PDF 时，先按本地 MinerU 流程转换 Markdown，再核对关键公式与原页。

阶段 1 完成时应交付：

- 一张带调用证据的模块与求解流程图。
- 单模型多线程和多模型吞吐量两份独立的并发说明。
- 按[基准规范](../benchmark-protocol.md)建立的 MindOpt / HiGHS 基线。
- 一组可证伪的改进假设，说明预期受益模型、成本和源码落点。
- 尚未解决的问题及其对结论的影响。

达到上述条件后再选择阶段 2 的第一项改动。目前的算例验证只证明安装可用。
