# 阶段 2：在 HiGHS 中验证改进

本阶段尚未开始实现求解器改动。先完成阶段 1 的证据与基线，再从已定位的瓶颈选择范围最小的一项实验。

HiGHS 基线已具备线程池、work stealing、并行 MIP、并行 dual simplex 和部分并行 IPM 数值内核。先核对参数、生效路径和实际利用率，再决定修改现有模块还是新增模块。[源码地图](highs-source-map.md)列出已核对的入口，不能把这些候选位置视为已测出的瓶颈。

每项实验在实施前记录：

1. 对应的阶段 1 证据、瓶颈和可被实验否定的假设。
2. 目标模型类别、预期指标、资源预算和收益/回归接受条件。
3. HiGHS 的具体源码落点、接口及共享状态约束。
4. 正确性验证、性能比较和撤回方式。

从 `codex/mindopt-performance-research` 保存的研究基线继续工作。较大的独立改动可各自建立 `codex/` 分支，使源码改动、实验参数和结果可以逐项评审。每个实验先保留未修改基线，再建立 Release 构建并执行相关 CTest/实例回归；并发改动还需验证单线程、不同线程数及重复运行的正确性。

实现使用 HiGHS 自有代码和独立设计表达；研究文档保留抽象机制与 Evidence 引用。SDK、原始伪代码、分析数据库、许可证及大型实验产物存放于本地 `mindopt/`。

每个提交说明问题触发条件、实现机制、正确性结果、代表模型上的收益与退化、测试范围。项目目标是改善可复现的性能；是否“对齐 MindOpt”需要由相同硬件、相同模型和相同终止质量的测量来判定。
